# نظام ERP متكامل

نظام تخطيط موارد المؤسسات (ERP) بواجهة عربية كاملة (RTL)، يغطي المخزون والمشتريات
والمبيعات وإدارة العملاء والمحاسبة والموارد البشرية، مع **محرك سير عمل ديناميكي**
تُعرَّف فيه حالات المستندات وقواعد الموافقة من الواجهة بدل تثبيتها في الكود.

## التقنيات

| الطبقة | التقنية |
|---|---|
| الإطار | Next.js 16 (App Router) + TypeScript |
| قاعدة البيانات | PostgreSQL 16 + Prisma 7 (عبر محوّل `@prisma/adapter-pg`) |
| المصادقة | NextAuth v5 (Credentials) مع صلاحيات حسب الدور |
| الواجهة | Tailwind CSS v4 + مكوّنات مخصّصة، خط Cairo، اتجاه RTL |
| منطق الخادم | Server Actions + التحقق عبر Zod |

## التشغيل محلياً

المتطلبات: **Node.js 20+** و**Docker Desktop** (لقاعدة البيانات).

```bash
git clone https://github.com/Albara005/project1.git
cd project1

npm install --legacy-peer-deps   # 1) الاعتماديات
npm run db:up                    # 2) تشغيل PostgreSQL في حاوية
npm run setup                    # 3) البيئة + الجداول + بيانات تجريبية
npm run dev                      # 4) التشغيل
```

ثم افتح <http://localhost:3000>.

`npm run setup` ينشئ `.env` ويولّد `AUTH_SECRET` عشوائياً وينتظر قاعدة البيانات
ثم يطبّق الهجرات ويعبّئ البيانات التجريبية. آمن للتكرار.

> ملاحظة: `--legacy-peer-deps` ضرورية بسبب خلل في إصدار npm الحالي عند حل شجرة
> اعتماديات Prisma، وليست متطلباً للمشروع نفسه.

### بدون Docker

إن كان لديك PostgreSQL مثبّتاً، تجاوز `npm run db:up` وأنشئ قاعدة البيانات
يدوياً، ثم عدّل `DATABASE_URL` في `.env` قبل تشغيل `npm run setup`:

```sql
CREATE USER erp WITH PASSWORD 'erp_dev_password';
CREATE DATABASE erp_db OWNER erp;
```

## الوحدات

- **المخزون**: المنتجات والفئات والمستودعات، أرصدة لكل منتج في كل مستودع، سجل
  حركات، تسويات جرد، وتنبيهات إعادة الطلب.
- **المشتريات**: الموردون وأوامر الشراء؛ استلام الأمر يزيد المخزون ويولّد قيداً
  محاسبياً تلقائياً.
- **المبيعات وCRM**: العملاء، الفرص البيعية، أوامر البيع؛ تأكيد الأمر يخصم من
  المخزون، وإصدار الفاتورة يولّد قيد الإيراد وضريبة القيمة المضافة.
- **المرتجعات**: مرتجع مبيعات يعيد البضاعة للمخزون ويخفّض الإيراد وذمم العميل،
  ومرتجع مشتريات يخرجها ويخفّض المخزون وذمم المورد. عند الربط بفاتورة أصلية
  لا يُسمح بتجاوز الكميات المفوترة (بخصم ما سبق إرجاعه).
- **المحاسبة**: دليل حسابات شجري، قيود يدوية متوازنة، قيود تلقائية من المبيعات
  والمشتريات والمدفوعات والرواتب، وتقارير (ميزان مراجعة، قائمة دخل، ميزانية،
  وقائمة تدفقات نقدية).
- **الموارد البشرية**: الموظفون والأقسام والوظائف، طلبات الإجازات بسير موافقة،
  وكشوف الرواتب مع ترحيل محاسبي عند الصرف.

## طباعة المستندات

لكل فاتورة ولكل إشعار مرتجع صفحة طباعة بمقاس A4 واتجاه RTL على المسار
`‎/dashboard/invoices/<id>/print` و`‎/dashboard/returns/<id>/print`، تعرض ترويسة
المنشأة والرقم الضريبي وبيانات الطرف والأصناف وتفصيل ضريبة القيمة المضافة
والمدفوع والمتبقي. الشريط الجانبي وأدوات الشاشة تختفي تلقائياً عند الطباعة
(`print:hidden`)، وزر «طباعة» متاح في صفحة الفاتورة وصفحة المرتجع.

المرتجع البيعي يُطبع كـ **إشعار دائن (Credit Note)** والمرتجع الشرائي كـ
**إشعار مدين (Debit Note)**.

### رمز ZATCA (الفوترة الإلكترونية — المرحلة الأولى)

فواتير المبيعات والإشعارات الدائنة تحمل رمز QR مطابقاً لمتطلبات هيئة الزكاة
والضريبة والجمارك: البيانات تُرمَّز TLV (وسم، طول بالبايت، قيمة UTF-8) ثم
Base64، وتشمل الحقول الخمسة الإلزامية — اسم البائع، الرقم الضريبي، الختم
الزمني ISO 8601 بتوقيت UTC، الإجمالي شامل الضريبة، وإجمالي الضريبة.

الرمز يظهر فقط على المستندات التي نحن البائع فيها؛ فواتير المشتريات والإشعارات
المدينة لا تحمله لأن البائع فيها هو المورد. ولا يُولَّد الرمز إن لم يكن الرقم
الضريبي مُعرَّفاً في إعدادات المنشأة. الكود في `src/lib/modules/zatca.ts`
ويوفّر `decodeZatcaQrPayload` لفك الترميز والتحقق.

## الفوترة الإلكترونية — المرحلة الثانية (التكامل)

على المسار `‎/dashboard/einvoicing`. ما هو مبنيّ ومُختبَر محلياً:

- **فاتورة UBL 2.1** بحقول الهيئة: UUID، وعدّاد الإصدار ICV، وتجزئة الفاتورة
  السابقة PIH، وتجميع الضريبة حسب النسبة.
- **سلسلة التجزئة**: كل فاتورة تحمل تجزئة سابقتها، فحذف حلقة أو تعديل محتوى
  فاتورة بعد إصدارها يكسر السلسلة. العدّاد والتجزئة يُقرآن ويُكتبان داخل
  معاملة واحدة حتى لا ينتج إصداران متزامنان نفس العدّاد.
- **التوقيع**: مفتاح secp256k1 وطلب شهادة بامتدادات الهيئة، وتوقيع
  ECDSA/SHA-256 يُدرج في الفاتورة بصيغة XAdES.
- **رمز QR للمرحلة الثانية**: تسعة حقول TLV تشمل التجزئة والتوقيع والمفتاح
  العام، فيتحقق المستلم دون الرجوع لأي خدمة.
- **عميل منصة فاتورة**: طلب شهادة التوافق، وفحوص التوافق، وشهادة الإنتاج،
  والتبليغ (للمبسطة) والإجازة (للقياسية)، مع حفظ رد الهيئة كاملاً.
- **فحص السلسلة** في الواجهة: يقارن العدّاد والتجزئة ومحتوى كل فاتورة.

### ما يتطلب إجراءً منك

**إصدار الشهادة يحتاج رمز تحقق (OTP) من بوابة فاتورة الخاصة بمنشأتك** — يصدره
صاحب المنشأة ولا يمكن توليده من النظام. لذلك اختُبر الأنبوب محلياً بشهادة
موقّعة ذاتياً، ولم يُختبر مقابل خوادم الهيئة.

قبل الاعتماد في الإنتاج يلزم: اجتياز فحوص التوافق في بيئة المحاكاة لدى الهيئة،
والتحقق من الـXML بأداة التحقق الرسمية. هذه الخطوات تحتاج تسجيلاً ضريبياً
فعلياً ولا تُغني عنها الاختبارات المحلية.

## قائمة التدفقات النقدية

على المسار `‎/dashboard/reports/cash-flow`، بفلتر فترة وفرع، وتُعرض بالطريقتين:

- **المباشرة**: تُقرأ حركات حسابات النقدية فعلياً من القيود المرحّلة، ويُصنَّف كل
  تدفق حسب تصنيف الحساب المقابل له في نفس القيد. القيود متعددة السطور يُوزَّع
  أثرها النقدي على أطرافها بنسبة مبالغها.
- **غير المباشرة**: تبدأ من صافي الربح وتُعدّله بالتغيّر في رأس المال العامل
  (الذمم المدينة والمخزون والذمم الدائنة والضريبة المستحقة).

التقرير يعرض مؤشرين للتحقق: **مطابقة التصنيف** (مجموع الأنشطة الثلاثة مقابل
التغيّر الفعلي في النقدية) و**تطابق الطريقتين** (النقد التشغيلي محسوباً بالطريقتين).
ظهور فرق في أيٍّ منهما يعني خللاً في البيانات أو في تصنيف الحسابات، ويُعرض صراحةً
بدل إخفائه.

تصنيف الحساب (تشغيلي/استثماري/تمويلي/نقدية) حقل على الحساب في دليل الحسابات
يعدّله المستخدم من الواجهة، لا قاعدة مثبّتة في الكود. الحساب بلا تصنيف يُعامل
كنشاط تشغيلي.

## محرك سير العمل الديناميكي

بدلاً من تثبيت حالات المستندات في الكود، تُخزَّن في قاعدة البيانات وتُدار من
`/dashboard/workflows`:

- **الحالات** (`WorkflowState`): مفتاح، اسم معروض، لون، وهل هي ابتدائية أو نهائية.
- **الانتقالات** (`WorkflowTransition`): من حالة إلى حالة، باسم إجراء يظهر كزر
  للمستخدم، مقيّد بـ:
  - **الأدوار المسموح لها** — مثلاً "الاعتماد" للمحاسب والمدير فقط.
  - **حد أدنى وحد أعلى للمبلغ** — مثلاً تأكيد أوامر البيع متاح للمندوب حتى
    20,000، وما فوقها للمدير وحده.
  - **ملاحظة إلزامية** — مثلاً عند الرفض أو الإلغاء.
- **النسخ** (`WorkflowInstance`) تربط كل مستند بحالته الحالية، و`WorkflowHistory`
  يحفظ من نفّذ كل إجراء ومتى وبأي ملاحظة.

يُسمح بتعريف نشط واحد لكل نوع مستند، وهو الذي يُطبَّق على المستندات الجديدة.
عند وصول مستند إلى حالة معيّنة يُنفَّذ الأثر المرتبط بها في نفس المعاملة
(خصم مخزون، توليد فاتورة، ترحيل قيد)، فلا تفترق حالة المستند عن أثره المحاسبي.

### ملاحظة للمطوّرين

لا تستورد `@/generated/prisma` أو `@/lib/db` أو `@/lib/modules/*` داخل مكوّن
يبدأ بـ `"use client"` — ذلك يسحب وحدات Node إلى حزمة المتصفح ويكسر الصفحة.
استخدم `@/lib/labels` للثوابت المشتركة، أو مرّر القيم كـ props من مكوّن الخادم.

بعد أي تعديل على `schema.prisma` شغّل `npx prisma generate` **وأعد تشغيل خادم
التطوير**؛ الخادم يحمّل عميل Prisma في الذاكرة عند الإقلاع، فيستمر في استخدام
النسخة القديمة ويفشل بـ`Unknown field` رغم أن الكود وفحص الأنواع سليمان.
